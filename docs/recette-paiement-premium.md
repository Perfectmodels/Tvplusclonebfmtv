# Recette Direct Premium — sans déploiement
Deux niveaux de test distincts.
## A. Recette locale sans argent
Dans une copie de développement de ce commit, définir PREMIUM_RECIPE_ENABLED=true et PREMIUM_RECIPE_SECRET (secret aléatoire >=32 caractères, ne jamais le commiter). Garder SINGPAY_ENABLED=false. Démarrer npm run dev. Ouvrir /direct/recette (local, ou Preview après autorisation explicite de déploiement et connexion administrateur settings.manage). Le parcours est désactivé en production et sur LWS hors développement. La recette utilise une référence et un cookie signé HttpOnly limité à l'API de recette, pas les tables paiements, pas SingPay, pas de droit réel, pas de vrai flux. Les prix sont fictifs. Pour la recette Preview, les identifiants de connexion de l'administrateur et l'API MySQL de recette doivent fonctionner. La recette locale ne dépend pas de la connexion MySQL pour son propre parcours (le layout peut cependant afficher des erreurs de contenu).
Tester : sélection et confirmation de l'offre ; moyen de paiement simulé Airtel/Moov ; retour en attente ; vérification positive ; lecteur de démonstration ; refus solde/code ; en attente ; annulation ; expiration ; répétition de la vérification ; réinitialisation ; aucune écriture sur tvp_live_payments et tvp_live_entitlements. Le cookie est une simulation par navigateur, pas un journal comptable ni un test de concurrence en base. Test unitaire : node --experimental-strip-types --test scripts/test-premium-recette.mjs (Node 22 récent).
## B. Test authentique SingPay
Documentation : https://github.com/singpay-ga/singpay-doc/blob/main/Etape-d%27int%C3%A9gration.md et https://client.singpay.ga/doc/reference/index.html.
Confirmer auprès du prestataire un portefeuille de test distinct, les identifiants de test et l'hôte exact de la page de paiement externe. Le guide avertit notamment que certaines opérations, par exemple PayPal, ne sont pas remboursées même en test. Ne jamais supposer qu'un paiement test est sans débit. Ne pas réutiliser les identifiants de production.
Sur la recette isolée avec schéma MySQL à jour : SINGPAY_MODE=sandbox ; SINGPAY_TEST_CLIENT_ID ; SINGPAY_TEST_CLIENT_SECRET ; SINGPAY_TEST_WALLET_ID ; SINGPAY_TEST_DISBURSEMENT_ID si requis ; SINGPAY_TEST_RETURN_ORIGIN (origine exacte de recette HTTPS) ; SINGPAY_TEST_CHECKOUT_HOSTS ; SINGPAY_TEST_WALLET_CONFIRMED=true uniquement après vérification réelle ; SINGPAY_ENABLED=true uniquement après contrôle du portefeuille. Sur LWS de recette hors Vercel, SINGPAY_TEST_ENVIRONMENT=true est nécessaire en mode Node production. Ne pas configurer ces variables sur l'environnement de production Vercel. Créer une offre de test active dans la base de recette via administration, puis ouvrir /direct, se connecter, sélectionner, confirmer, suivre le véritable lien SingPay, revenir /direct/paiement, vérifier auprès de SingPay, contrôler l'historique et le rapprochement. Le test ne crée jamais de droit réel ; le lecteur de démonstration de la recette A n'est pas un test du flux sécurisé.
Avant toute commercialisation : GoLive, lecteur vidéo avec jetons effectivement vérifiés, cron de rapprochement et validation des tarifs, migration SQL et recette complète. Aucun déploiement ni paiement externe autorisé par ce document.
